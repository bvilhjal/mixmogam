# Scale, invariance and calibration study (prespecified)

Protocol written 2026-10-25, before the first measurement of the study it
describes. The driver is `scale_study.py`; the archive records the SHA256
of this file, so a later reader can check that the plan predates the
numbers it is asked to explain.

## Why this study exists

The suite's measured evidence stops below the scale at which the
package's own claims are made. No archived run exceeds 80,000 variants,
and the 19 and 25 October efficiency reviews say so explicitly:

* the variational Gram cache holds about 278,000 variants at the default
  1 GB budget, so every archive so far sat entirely inside the cache and
  never measured the recompute tax that starts at the cliff;
* the LD-score window and the cross-validation matrix of the mixture
  model are only large at genome scale;
* every archived measurement used the optional acceleration package and
  a pinned single-threaded math library, so neither the default
  installation nor the default threading has ever been measured.

This study closes those three gaps. It does not attempt to re-measure
what the archives already hold.

## Estimands

1. **Resource use at genome scale.** Wall time, CPU time and peak
   resident set size of one complete association fit, per method, at
   5,000 samples and 400,000 variants, on a panel with realistic
   density.
2. **The Gram-cache cliff.** The change in time and memory when the
   variational Gram cache is switched off, kept at its default 1 GB
   budget, or raised until the whole panel fits. The prediction is
   fixed before the run: at 400,000 variants and one covariate column a
   1 GB budget holds about 320,000 of the panel's sub-blocks, so the
   default configuration is expected to be slower than a full cache and
   much slower than no cache only if the sweeps touch the uncached
   blocks repeatedly. The measurement decides.
3. **Configuration invariance.** Whether the reported statistics depend
   on the memory budget, the thread count, the genotype storage format
   or the presence of the optional acceleration package. These are
   implementation choices, so the p-values must not depend on them.
4. **Calibration and power.** Type-I error of each method under a
   genetic null, its power over large-effect variants, the attenuation
   of its effect estimates, and the effect of population structure and
   of an environment that differs between populations, each with Monte
   Carlo uncertainty.
5. **The default installation.** The cost of the pure NumPy fallbacks
   relative to the accelerated kernels, and whether the package warns
   that it is using them.

## Design

Three panels, all generated by `phensim` from recorded seeds.

| Panel | Samples | Variants | Chromosomes | Structure | Used by |
|---|---:|---:|---:|---|---|
| P1 invariance | 1,500 | 20,000 | 8 | none | arm A |
| P2 calibration | 1,000 | 10,000 | 8 | none, and 4 populations at F_ST 0.3 | arm B |
| P3 scale | 5,000 | 400,000 | 20 | none | arms C and C2 |
| P4 default install | 1,000 | 20,000 | 8 | none | arm D |

Genotypes come from founder haplotypes in blocks of 100 variants
(`phensim.simulate_haplotype_blocks`), so LD is present inside a block
and decays between blocks. The structured panel of arm B comes from
`phensim.simulate_population_structure` with Balding-Nichols
frequencies and AR(1) blocks at rho 0.9. Positions are synthetic
(5 kb spacing inside a chromosome); they matter only for the LD-score
window, whose density is stated with the results.

Phenotypes are polygenic with the requested heritability. A mixed
trait is built from two genetic parts: a background of small effects on
20% of the variants (the part an infinitesimal model can represent)
and ten large-effect variants that carry half of the genetic variance
(the part that carries the power). A null trait has no genetic
component at all; a confounded trait adds an environment that differs
between populations, which is the environment the analysis does not
know about.

### Arm A: invariance

One panel, one phenotype, five methods: the dense exact LOCO reference
(`exact`), `bolt-inf`, `bolt`, `hratt` with the projected heritability
estimator (`hratt-he`) and `hratt` with REML (`hratt-reml`). Each
method is run in the configurations that apply to it:

| Configuration | Change | Question |
|---|---|---|
| `ref` | threads 1, native libraries pinned to 1, default cache | reference |
| `cache0` | `gram_cache_bytes=0` | no Gram cache |
| `cachefull` | `gram_cache_bytes=2e9` | whole panel cached |
| `threads4` | four workers, native libraries pinned to 1 | thread count |
| `packed` | two-bit genotype storage | storage format |
| `nonumba` | the acceleration package is not importable | default installation |

The Gram cache belongs to the variational engine, so `cache0` and
`cachefull` do not apply to `exact` and `bolt-inf`; the worker option
exists only in the exact path and in HRATT, so `threads4` does not
apply to `bolt-inf` and `bolt`, whose native libraries stay pinned in
every configuration. A configuration that does not apply is absent from
the archive rather than run and reported as a duplicate.

The p-values of every configuration are compared with the reference
configuration of the same method. The decision rule is fixed: the
configurations must be *identical* (bitwise) except for `threads4` and
`nonumba`, where a difference up to 1e-6 in log10 p is accepted
(parallel reductions and the pure Python kernels reassociate floating
point sums). Any larger difference is a finding, not a tolerance.

### Arm B: calibration and power

Five cells, ten independent replicates each, a fresh panel per
replicate, five methods per cell.

| Cell | Panel | Trait | Covariates |
|---|---|---|---|
| B1 null | unstructured | h2 = 0 | none |
| B2 mixed | unstructured | h2 = 0.5, ten large-effect variants, background on 20% of the variants | none |
| B3 null | structured | h2 = 0 | none |
| B4a confounded | structured | as B2, half the liability on an environment that differs between populations | none |
| B4b confounded with PCs | structured | as B4a | the two leading genotype principal components |

Reported per cell and method: genomic control lambda, the type-I error
at 0.05, 0.01 and 0.001 with its binomial 95% interval over the
variants that carry no effect, the power at 0.05/m and 5e-8 over the
ten large-effect variants with its binomial 95% interval, and the
attenuation of the per-variant effects, measured as the slope of the
estimated effect on the true effect over those variants. A variant with
no statistic (a monomorphic marker) is not a tested variant and is
left out of the denominators. The exact LOCO EMMAX fit is the
reference in every cell. Nothing is tuned after the results are seen,
and a replicate that fails to converge is reported as such rather than
replaced.

### Arm C: scale

Panel P3 (5,000 x 400,000) with the four two-step methods
(`bolt-inf`, `bolt`, `hratt-he`, `hratt-reml`) in six configurations:
`ref`, `cache0`, `cachefull`, `threads4`, `blasdefault` (no thread
pinning at all, the configuration a user gets) and `packed`. Each fit is
a fresh process; peak RSS is the operating-system figure for the whole
process, so the genotype panel is included and reported separately.
The dense exact path is not run at this size: its cost is cubic in the
sample size and would dominate the study without answering a question
about the two-step engine.

### Arm C2: the cache cliff ladder

One method (`hratt-he`) on four panels of the same size and shape --
5,000 samples and 100,000, 200,000, 400,000 or 600,000 variants -- each
run twice: with the default 1 GB Gram cache and with a 2 GB budget that
covers the whole panel. The engine charges every sub-block of 128
variants `(folds + 1) * (128 * 4 + 8 q)` bytes, so at one covariate
column and five folds the default budget covers about 320,500 variants:
panels at 100,000 and 200,000 variants fit entirely, the 400,000-variant
panel leaves about a fifth of its variants uncached, and the
600,000-variant panel leaves about half. The predicted coverage is
written next to every measurement, so the cliff can be read off the
table instead of inferred.

### Arm D: default installation

A smaller panel (1,000 x 20,000) with the acceleration package present
and absent, for `bolt-inf`, `bolt` and `hratt-he`. The ratio of the two
is reported as measured on that panel, with the per-cell cost of each
path, so that a reader can see the scaling rather than a bare factor.
The run also records whether the package warned that it was using the
fallbacks: it must, or the default installation is silently slow.

## Analysis and provenance

* One measurement is one fresh process. Wall time, user and system CPU
  time and peak RSS come from the child's operating-system counters
  (``os.wait4``), never from allocation tracing.
* Panel construction is inside the measured process but outside the
  reported fit time; both numbers are recorded.
* Threads are pinned for every configuration except `blasdefault`, whose
  point is to show the unpinned default.
* The load average is recorded before every measurement and the run
  waits for a quiet host when asked.
* The archive holds the source snapshot of the package and of `phensim`,
  the environment manifest, the hash of this plan, every worker's
  command, log and measurement, the per-variant p-values of every fit,
  and the agreement tables computed from them.
* Failures stay visible: a worker that dies leaves its log in the
  archive and stops the arm.

## What this study cannot show

* It is one host, one panel family and a handful of replicates. It is
  not a calibration study of a human cohort.
* The dense reference exists only at the small sizes of arms A and B.
  At arm C the two-step methods are compared with each other, not with
  an independent implementation.
* The absence of a Numba path is measured on the fallback code as it
  stands; if that code is later vectorized the numbers change.
* Nothing here compares with LDAK-KVIK; the matched comparison with the
  official program stays in `ldak_kvik_comparison.py` and its archives.
